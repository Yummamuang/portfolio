Loop engineering

Designing the system that prompts a coding agent, instead of prompting it turn by turn.

The problem

Prompting an agent one turn at a time makes me the loop. I decide what comes next, I check every result, and I decide when the work is done. The agent is fast; the loop around it is me, and my checking gets sloppy long before the agent gets tired.

The idea

A loop has four parts:

  1. Goal, checked on every pass, with a stop condition you can prove.
  2. Action, the agent works toward the goal from where it is now.
  3. Observation, the system measures the result: tests, lint, build, diff.
  4. Adjustment, the feedback shapes the next pass.

The verifier sets the quality of the loop, not the model. A weak verifier lets a loop converge on a wrong answer with full confidence. So I order verifiers by how far I can trust them: deterministic checks first (exit codes, tests, lint, typecheck, a clean build), then a separate agent judging against a rubric, and a human for anything that cannot be undone. The agent that wrote the code never grades it.

How mine works

One item per pass. A bare /loop in Claude Code reads this prompt. It picks exactly one thing and has rules that close the usual escape hatches. 

Work the current branch. Pick exactly ONE thing, in this order:

1. If `work-memory/STATE.md` exists and has an item marked `next`, do that item.
2. If the gate is red (`.claude/gate.sh`, or lint/format on changed files), fix it.
3. If the branch has a PR with failing CI or unresolved review comments,
   address the oldest one.
4. Otherwise say "nothing pending" in one line and stop the loop.

Rules:
- One logical change per iteration. Never batch unrelated fixes.
- Never modify a test to make it pass. Fix the code.
- Do not commit or push unless STATE.md or the user explicitly asked for it.
- If the same item fails twice in a row, stop and report what is blocking.
- Update STATE.md before you finish the iteration.

State outside the chat. Work that spans sessions lives in a STATE.md file, not in the conversation. Every session reads it first and updates it last. 

# STATE
Updated: YYYY-MM-DD
Goal: <the goal for this round, something you can measure>

## Next
- [ ] `next` <the one item to do next>
- [ ] <after that>

## Done
- [x] <done, with the commit or PR>

## Blocked
- <what is stuck and what it needs from a person>

## Learned
- <an error already hit and its fix, or an approach that failed and why>

A gate before the agent stops. A Stop hook runs whenever the agent tries to end a turn while files have uncommitted changes. It skips the check when every changed file is docs or config. Otherwise it runs the repository's own gate script, or a default one scoped to the changed files: ESLint, Prettier, and vitest run on each changed file's colocated test. If the gate is red, the hook blocks the stop once and hands back the last 60 lines of output, so the agent's next pass starts from the failure. My task workflow also runs a fuller pass at the end of each task, including the matching .NET test class.

Stop rules. A loop without a stop is an open invoice. Mine stops when nothing is pending, takes one change per pass, and stops to report when the same item fails twice in a row. I also built a fully unattended outer loop with an iteration cap, a no-progress check and a spend cap, and later set it aside.

What it changed

An agent that tries to end a turn on a red gate is sent back once with the failing output. Work that spans several sessions picks up from STATE.md instead of from whatever I remember. Each pass is one reviewable change.

What stays with me

The inner loop, investigate, implement, verify, repeat, is delegated. The outer loop, deciding to ship or block and owning the result, is not.

Delegating the inner loop is leverage; delegating the outer loop is abdication.
