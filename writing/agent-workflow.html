Plan first, then one subagent per task

How I ship with coding agents: a written plan, a fresh subagent for each task, and a review after every step.

The problem

One long agent session piles up context from every step, and the agent ends up checking its own work.

1. Write the plan

The plan is written for an engineer who knows nothing about the codebase. Every task lists:

  • the files it creates or changes, shared files included, so tasks that would collide never run together;
  • the names and types it uses from earlier tasks and hands to later ones;
  • for a task that implements a business rule, the rule quoted word for word from the ticket, marked as a property that must hold for every input or as boundary examples;
  • for a code task, its test file, named after the file it covers;
  • for anything a user can see, browser steps with an observable result for each.

When a task changes something a user can see, the plan ends with an end-to-end demo flow. I also get a short plain-language summary in chat before I approve the plan. The rules are approved before any code is written.

2. One subagent per task

Each task goes to a fresh subagent that sees only its own brief, not the whole conversation. Tasks that do not depend on each other and touch no shared file run at the same time, in waves worked out from the plan's dependencies.

3. Review every task

After each task a separate reviewer checks it against the spec and for code quality. When the task changed something a user can see, a browser test follows the plan's steps in a real browser.

4. Review the whole branch

One broad review of the whole branch runs at the end, before anything ships.

What it looks like

One task from the plan that built this site, trimmed:

### Task 9: Work program

**Depends on:** Task 4, Task 8

**Files:**
- Create: `src/work/projects.ts`
- Test: `src/work/projects.test.ts`
- Create: `src/work/work-panel.ts`
- Test: `src/work/work-panel.test.ts`

**Rules:**
- PRODUCT.md principle 1: "Proof over claims. Every project
  points to a demo, video, or repo the reader can open."
  · checked over the whole list: every project link starts
  with https:// or the site base.

What it changed

This site was built this way, and the reviews caught problems the tests could not see:

  • The dial passed its unit tests, but a browser review found a layer of labels covering the knob, so it could not be dragged with a mouse.
  • Two tasks ran at the same time and one commit picked up the other task's files. A reviewer read the commit list, and the history was split before anything was pushed.
  • A sentence in the loop write-up said more than the hook actually does. The review compared it with the script, and the copy was corrected.

Why it works

The agent that writes the code is never the one that approves it. Each subagent starts clean, so context from one task cannot leak into the next. And the rules a test must prove are agreed with a person before the first line of code.
